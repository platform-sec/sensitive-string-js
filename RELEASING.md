# Releasing

SensitiveString packages release independently. A change to one provider or framework adapter does
not force unrelated packages to take a new version, while Changesets still propagates an internal
release when a dependency range must change.

## Why independent versions

The packages have different compatibility surfaces and release cadences. Lockstep releases would
make an AWS-only fix look like a new Express, Sentry, and Kubernetes release. Independent versions
make each package's history and stability legible to its users.

There are two costs:

- A cross-package feature can produce several versions and tags in one release.
- Before 1.0, `^0.1.0` does not accept `0.2.0`. A core minor release therefore requires patch
  releases of dependents whose peer ranges must expand.

The second cost is intentional. Publishing those dependent patches prevents npm from reporting a
peer conflict even when the dependent's own implementation did not change.

The current package graph makes the practical impact predictable:

| Proposed change                                | Expected releases in the current graph              |
| ---------------------------------------------- | --------------------------------------------------- |
| Patch `sensitive-core` from `0.1.0` to `0.1.1` | Core only; `^0.1.0` still accepts it                |
| Minor `sensitive-core` from `0.1.x` to `0.2.0` | Core plus its 26 direct dependents                  |
| Minor `sensitive-http` from `0.1.x` to `0.2.0` | HTTP plus its five client wrappers                  |
| Patch or minor a leaf provider or adapter      | That package only                                   |
| Change several public packages together        | Selected packages plus only out-of-range dependents |

That means independent versions buy the most for leaf packages, which make up most of this
workspace. A pre-1.0 core minor still looks close to a lockstep release because almost every package
peers on core; that is a property of the compatibility graph, not a reason to give unrelated leaf
changes new versions forever.

## Contributor workflow

For a user-visible change, run:

```bash
pnpm changeset
```

Select every package whose own public behavior changed and choose its SemVer impact. Do not select
packages merely because they depend on one of those packages; Changesets computes required internal
range updates. Commit the generated `.changeset/*.md` file with the implementation.

Changes that cannot affect a published package, such as CI-only or documentation-only edits, do not
need a changeset.

## Version Packages pull request

After changesets reach `main`, the Version Packages workflow maintains one pull request by running:

```bash
pnpm release:version
```

Enable **Settings > Actions > General > Allow GitHub Actions to create and approve pull requests**
for the repository; the workflow cannot create its branch and pull request without that setting.

That command consumes the pending changesets and updates package manifests, package changelogs,
internal ranges, and the lockfile. These files are reviewed and committed together. Do not manually
edit a package version or a generated package changelog during normal release preparation.

Review the pull request for:

1. The intended direct package bumps.
2. Any dependent patch bumps and peer-range changes, especially after a pre-1.0 minor bump.
3. One changelog entry for every new package version.
4. A lockfile that agrees with the manifests.
5. Passing CI and `pnpm release:check`.

The root [`CHANGELOG.md`](CHANGELOG.md) remains the historical project-wide narrative. Package-level
`CHANGELOG.md` files generated by Changesets are the source for package release notes.

Every package has a committed `0.1.0` bootstrap entry because none has been published yet. The first
release plan therefore contains all 28 packages at that baseline. That one-time common starting
point does not put later releases into lockstep.

If the first public versions should be higher than `0.1.0`, add and merge the changesets that express
those bumps before dispatching a non-dry release. The publishing workflow deliberately does not
infer release maturity or choose a version on the maintainer's behalf.

## Publishing

Merge the Version Packages pull request, then manually dispatch the Release workflow. Start with
`dry_run` enabled. The workflow:

1. Reads committed package versions and asks the npm registry which are unpublished.
2. Validates manifests, internal ranges, package changelogs, and the publish plan.
3. Builds and packs the exact tarballs in dependency order.
4. Signs those tarballs with keyless Cosign and verifies the signatures.
5. In a real run, publishes those same signed bytes with npm provenance.
6. Creates package-specific git tags and one GitHub release for the publication batch.

The workflow never calculates or writes a version. If a version, range, changelog, or lockfile is
wrong, repair it through the Version Packages pull request before publishing. A release also refuses
to proceed while any unconsumed changeset remains on `main`.

The `npm-publish` GitHub environment should require maintainer approval. The workflow currently
expects an `NPM_TOKEN` secret and requests an OIDC identity for npm provenance and Cosign signing.
Real publication is additionally restricted to a workflow dispatched from `main`; dry runs may be
used on another ref while testing release automation.

Changesets v3 is pinned exactly. Its release-plan and version behavior are used directly, while the
repository's `release:pack` compatibility script supplies the one operation its built-in pack command
cannot perform through the project's pinned pnpm 9. Review that boundary before upgrading either
tool.

The single batch release is deliberate. Package tags still use the standard `name@version` form,
but one GitHub release prevents the existing SBOM and SLSA workflows from rebuilding and attaching
the entire workspace once for every package in the same batch.
